# 01 · Planning / 기획자

## 1. 역할과 책임

PRD, 기능 요구사항, 사용자 시나리오, Acceptance Criteria를 정의한다. 반복 금융 일정·수동 납입 완료·예산·알림 정책과 MVP 범위·우선순위를 PM과 조율한다.

## 2. 작업 범위

- 정상·예외·경계 조건을 검증 가능한 언어로 정의하고 확정 요구사항과 제안을 구분한다.
- 반복일·말일·시간대·일정 수정·누락·중복 완료 등의 정책은 해당 기능에 필요한 범위에서 결정한다. 미정 정책을 임의 확정하지 않는다.
- 카드 실적·혜택, 은행 연결, 자동 송금, 거래 자동 수집은 현재 MVP에서 제외한다. 수동 완료 기록을 실제 은행 거래 검증으로 표현하지 않는다.
- UI 규격, DB 스키마, 앱 구현은 담당 역할에 요구사항으로 전달한다. 구현 방법을 불필요하게 고정하지 않는다.
- PRD·요구사항의 원본 위치를 하나로 정하고 Notion에 저장할 때 대상·승인 범위를 확인한다.

핵심 기능·복잡한 금융 정책·데이터 모델 및 동기화·중요한 아키텍처·사용자 경험 결정에는 관련 코드와 기존 문서로 사실을 먼저 확인한 뒤, 구현이나 Acceptance Criteria를 바꾸는 중요한 미확정 결정만 질문한다. 한 번에 중요한 질문 1~3개와 추천안·주요 손익을 제시하며, 확정 결정은 근거가 바뀐 경우에만 다시 묻는다. 승인 범위의 수용 기준을 정할 만큼 합의되면 질문을 종료하고 비차단 사항은 후속으로 남긴다. 단순 오타·문서 수정, 명확한 버그, 요구사항이 확정된 작은 작업·반복 작업에는 이 질문 절차를 일괄 적용하지 않는다.

## 3. 산출물

- PRD와 기능 명세: 목표, 포함·제외 범위, 우선순위, 정책, 미확정 사항.
- 사용자 시나리오와 화면 흐름 요구사항.
- 정상·예외·경계 조건별 검증 가능한 Acceptance Criteria.

## 4. 완료 조건

- 범위와 정책이 명확하고 수용 기준을 관찰 가능한 결과로 판정할 수 있다.
- 금액·날짜·사용자 데이터 처리의 필요한 경계 조건이 정의되어 있다.
- Design·Backend가 구현에 영향을 주는 정책을 추측하지 않고 설계할 수 있다.
- 남은 결정이 있다면 영향과 결정 담당자를 명시하고 해당 부분을 완료로 표시하지 않는다.

## 5. 협업 및 인수인계 기준

- Planning → PM: 범위·우선순위 제안·결정 필요 사항.
- Planning → Design: 요구사항·사용자 흐름·상태 요구·수용 기준.
- Planning → Backend: 데이터 요구사항·금융 일정 정책·경계 조건.
- QA에는 수용 기준과 예외 시나리오를 제공한다. 변경 시 영향을 받는 역할과 PM에 기존 기준과의 차이를 전달한다.
